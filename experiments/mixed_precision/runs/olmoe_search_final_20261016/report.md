## 結論：逐題回答

**1. CPU／GPU 差異是否找到原因？——找到了，而且可以分成三層。**

- **[量測] 設定不一致：排除**。以下各項在 CPU 和 GPU 上逐位元相同：token、loss 計算方式、16 層的 expert ID 和 routing weight、FP32 權重、三個 Posit LUT，以及兩個配置共 6144 個投影的量化權重。
- **[量測] 量化器實作差異：存在，但影響極小，已修正**。
  - GPU 的 int 活化量化器是除以一個放在 CPU 上的 0 維 scale 張量。給它和 CPU 完全相同的輸入，每個窗口約 1.5 億個量化值中，有 1–5 個 int7 code 不同。
  - 改成「scale 和 zero-point 放在輸入所在裝置」的修正版後，不一致變成 0。
  - 逐層同步追蹤時，凡是兩邊輸入逐位元相同的位置，輸出也全部相同。
- **[量測] 主因是上游浮點差異被量化放大**：
  - 未量化的 FP32 部分，CPU 和 GPU 每層只差約 3e-7（相對 L2）。
  - 但到第 0 層的量化器時，已有約 77% 的輸入元素在低位元上不同，造成 1,220–6,133 個量化值翻轉。
  - 這些翻轉逐層擴散：到第 15 層，同一個配置在兩個 backend 上的 hidden state 相差 4–5%，和「LP 配置 − MILP 配置」本身的差異（約 4.8%）同一量級。
  - 從第 2 層起，兩個 backend 上的「LP − MILP」差異向量幾乎互不相關。
- **[量測] 這種放大在 GPU 上也能單獨重現**：只把嵌入層輸出乘上 (1 ± 2⁻²³)，FP32 的 CE 幾乎不變（≤ 9e-7），但量化配置的單窗口 CE 變動標準差約 0.0095 nat/token，最大到 0.030。這和 LP − MILP 單窗口配對差的標準差（0.010–0.011）相當。
- **[量測] CPU 自己也不穩定**：系統有負載時，OpenMP／MKL 會動態調整執行緒數，量化配置的單窗口 CE 最多因此變動 0.019 nat/token。設 `OMP_DYNAMIC=FALSE MKL_DYNAMIC=FALSE` 後，在負載下也逐位元可重現；單獨執行時本來就可重現。
- **[量測] 差中之差沒有統計上可解析的差異**：在原本的 16 個共同窗口上，(LP − MILP)_CPU − (LP − MILP)_GPU = +0.0054，95% CI [−0.0011, +0.0126]，包含 0。
- **未解問題**：
  - 上一輪回歸那次 CPU 執行，現在所有單獨執行都無法重現；當時的系統負載已無從查證。
  - 最早的 FP32 差異究竟出自 attention、norm 還是 linear，沒有再細分。
  - 「逐一替換 7 個投影」的診斷沒有做：放大過程是混沌的，單一替換的效果無法乾淨地分離。

**2. 完整修正後的 MILP knee 是否仍在 R ≈ 0.707？——是。** [量測]
- knee 在 R 0.7071056，BC 18.29196。它來自第 1 輪 refinement 的預算 0.7071062。
- 它和舊的參考點 `bc_p125`（R 0.7071066，BC 18.29187）屬於同一群近重複點，knee 分數只差 1.9e-8，但配置差 11 個投影。

**3. LP 的近似誤差是否改變細化搜尋與最終 knee？——改變了細化路徑和最終配置，但沒有改變 knee 的位置。** [量測]
- LP knee 和修正後 MILP knee 差 4 個投影：R 低 6.4e-5，BC 高 0.029%，knee 分數只差 6.7e-7。
- 兩者的分岔有兩個來源：
  - LP 取整後剩下一點資源沒用完：在預算 0.7071068 上，LP 解的實際資源是 0.707061，MILP 是 0.7071066。
  - MILP 自己的第 1 輪 refinement 產生了一個近重複點（R 0.7071056），它成為新的 knee，讓第 2 輪改往左側取樣。
- 把所有方法和對照求解合併後，frontier 的前 4 名都在 R 0.70706–0.70711 之間，分數差 ≤ 7e-7。R 差超過 0.5% 的次佳點，分數低 1.1e-4（LP）到 4.0e-4（MILP）。

**4. 純 LP、LP 優先相對修正後的 MILP 快多少？** [量測，各量一次，依序單獨執行]

| 方法 | auto_select | 相對修正後 MILP |
|---|---:|---:|
| 修正後 MILP | 3294.8 s | 1× |
| 純 LP＋取整＋修復 | 14.3 s | 約 231 倍 |
| LP 優先（2 個預算退回 MILP） | 76.5 s | 約 43 倍 |

- 每種方法只量了一次，所以這不是穩定的加速比。
- 建問題的成本另計：讀表 0.03 s、支配刪除 4.1 s。

**5. 新資料是否支持品質等價？——GPU 主評估支持。** [量測]
- 512 個新窗口：LP − MILP 的配對差 +0.00062 nat/token，95% CI [−0.00030, +0.00154]，完全落在 ±0.002 內，依預先登記判為等價。
- LP 優先和純 LP 選出的配置相同，所以只有一組比較，不需要多重比較校正；97.5% CI [−0.00041, +0.00169] 也在範圍內。
- CPU 子集（16 個窗口）分開報告：+0.0013，CI [−0.0024, +0.0055]。樣本太少，無法判定；但也沒有和 GPU 矛盾，兩者差 +0.0010，CI [−0.0037, +0.0061]。

**6. 研究方案與預設**
- **[推論] fixed-route OLMoE 的研究方案：保留「LP 優先」**。
  - 它和純 LP 選出相同的 knee，品質和完整 MILP 等價。
  - 在 LP 差距較大的兩個預算（R 3.36、6.73），它退回 MILP，得到和 MILP 相同的解。
  - 時間是 MILP 的 1/43。純 LP 則適合需要更快的探索性掃描。
- **不足以改成預設，還缺以下證據**：
  1. **dense 模型**：上一輪回歸中，LP 優先在 Qwen3 和 Qwen3.5 FFN+attn 選出不同的 knee，該回歸沒有通過。
  2. **knee 規則本身**：分數差到 1e-6–1e-8 的近重複點會改變 refinement 方向。這次 MILP 自己就遇到了。需要一個能處理近重複點的 knee 規則，並另行驗證。
  3. **計時**：只量一次，沒有重複量測。
  4. **下界不嚴格**：LP 和 MILP 的下界在小目標值時都不是嚴格保證（見實驗 B 的數值檢查）。
  5. **適用範圍**：只有一個 MoE 模型、一個 BC 表、一組 calibration，而且只做了 fixed route。
  6. **CPU 交叉檢查**：只有 16 個窗口，無法獨立確認 ±0.002 的等價。

**[推論]**
- 量化模型對 FP32 等級的擾動是混沌的：只要有一個值翻轉，就會一路擴散。
- 每個窗口的配對差裡，有一個大小約 0.01 nat/token 的成分，它取決於浮點實作的細節（backend、執行緒數、量化器的除法路徑），而不是取決於配置本身。
- 若這個成分在窗口之間互相獨立，它已經包含在 bootstrap 的變異裡；在 512 個窗口下，它讓平均值移動的幅度大約等於一個標準誤（約 0.0005）。
- 這是由證據支持的機制，不是假定的「雜訊」。

## 實驗 B：完整重跑修正後的搜尋（`B/`）

三種方法共用以下設定：
- 原 BC 表，經精確支配刪除後剩 70,153 個選項。
- GRID11 × GRID11，資源定義 R = max(M/M8, B/B8)。
- `mp_auto.auto_select`：17 個樣本、2 輪 refinement，端點與 knee 規則都不變。
- HiGHS 1.12 MIP，`mip_rel_gap` 0，時限 300 s。

修正後 MILP 的規則：保留原本的 1 ppm 重試；只有在重試也失敗、而第一次求解有解時，才修復第一次的解，並標記為「修復，非證明最佳」。

|---|---|---|---|
| 呼叫次數／失敗 | 23／0 | 23／0 | 23／0 |
| 路徑 | 精確 6、1 ppm 重試 16、修復 1（R 0.5） | LP 23 | LP 21、退回 MILP 2（R 3.36 重試、R 6.73） |
| auto_select 時間 | 3294.8 s（第一次求解 1762 s＋重試 1531 s） | 14.3 s（LP 11.9 s、取整與修復 0.6 s） | 76.5 s（LP 12.0 s、MILP 62.1 s） |
| knee R／BC | 0.7071056／18.29196 | 0.7070606／18.29732 | 同純 LP |

**MILP 的每次求解**（從 HiGHS log 解析，`logs/`）[量測]
- R ≤ 1.41 的每次求解約 87–130 s，其中 presolve 佔 82–109 s；首個可行解出現在 presolve 結束後 1.4–19 s。
- R 0.5：第一次求解的解超出預算 2.5e-7，1 ppm 重試無解（status 2），修復 1 次交換後可行，目標值和第一次求解的 dual bound 相對相差 1.3e-8。

| 方法 | 第 0 輪 knee（左／右鄰居） | 第 1 輪新增 | 第 1 輪後 knee（左／右） | 第 2 輪新增 | 最終 knee |
|---|---|---|---|---|---|
| MILP | 0.7071066（0.5946／0.8409） | 0.6484、0.7071062、0.7711 | **0.7071056**（0.6484／0.7071066） | 0.6626、0.6771、0.6920 | 0.7071056 |

**knee 分歧的原因**（依題目要求的分類）[量測]
1. **同預算的解品質**：在 R ≤ 2.83 的同一個預算上，LP 的 BC 比 MILP 高 1e-6 到 5.5e-4（相對），配置差 2–11 個投影。
2. **取整剩餘資源**：LP 在預算 0.7071068 上的實際資源只有 0.707061。第 1 輪中間點也因此不同（MILP 0.7071062，LP 0.7070917）。
3. **近重複點改變鄰居**：MILP 在 0.7071062 得到一個 R 只差 9e-7 的新點，它成為 knee，把第 2 輪拉到左側。
4. **knee 分數接近**：合併 frontier 的前 4 名分數差 ≤ 7e-7。
5. **端點**：三種方法都有 R 0.5 的點；MILP 是靠修復得到的。端點不是分歧的原因。

**對照求解**（`controls.json`，計時另計 676 s）[量測]
- MILP 補解 LP 取樣過的預算：0.6771、0.7071、0.7384，各 210–245 s。
- LP／LP 優先補解 MILP 取樣過的預算：每次約 0.8 s。
- 結果：MILP 在 LP 的 knee 預算附近（0.7070758）得到 18.2956，knee 分數排第 3。knee 群集內的排序取決於樣本落在哪裡。

**數值檢查**（`analysis.json` 的 `numerics`）[量測]
- HiGHS 警告「Problem has some excessively small costs」：成本從 4e-12 到 763，縮放後 [5e-11, 1e4]。
- MILP 在 R 1.414 的下界比自己的目標值高 8.5e-9，標記為可疑。
- MILP 在 R 8 宣稱最佳（1.7e-10），但 LP 取整後的可行解是 4.0e-12，更好。兩者都低於求解器的絕對解析度（1e-6 × 0.0763 = 7.6e-8），所以這一點標記為「低於解析度」。
- 結論：在小目標值時，LP 和 MILP 的下界與「最佳」狀態都不能視為嚴格保證。knee 附近（BC ≈ 18）的差距是 1e-5 等級，沒有矛盾。

## 背景核對與修正紀錄

- 題目列的背景 1–6，和程式及原始數據一致（`plan.json` 的 `background_verified`），但有以下細節：
  - 上一輪的 CPU 子集沒有重播 FP32；
  - 「純 LP 17 s」是速度實驗量的；
  - 「LP 優先 54 s」是在另一個回歸行程同時執行時量的，而且它退回時用的是「MILP＋修復」，不是重試版。
- multipoint 報告把 R 0.5 失敗的原因寫成「時限內無解」，實際原因是 1 ppm 重試讓問題變成無解。該報告本輪沒有修改。
- **amendments**（`plan.json`）：
  1. 16:33：CPU 的 4 窗口重複執行和 16 窗口子集批次形狀不同 → 補做相同形狀的重複執行，以及 matmul 對齊微測試；
  2. 16:37：單獨重複執行完全相同 → 補做有負載、有負載但關閉動態執行緒的對照，以及 16 窗口子集的單獨重播；原本計畫的 MKL_CBWR 測試取消；
  3. 17:09：補做「只算兩個 knee」的重播；
  4. 17:13：之後所有 CPU 工作一律關閉動態執行緒；實驗 A 的 CPU 基準改用單獨執行的結果；
  5. 17:20：依預先登記的修正規則，之後的 GPU 評估（A5、C）改用修正後的量化器；先前的結果保留、分開報告，BC 表不重算。
- 修正前後的結果沒有混在一起：A1／A3 使用原量化器；A5 三種變體分列；C 只用修正後的量化器。
